# 兼容性模型

恢复助手不应该把每个小版本号都硬编码成一条白名单。版本号只能帮助说明已知环境，真正决定能否安全写入的是本地状态结构、数据库完整性、项目身份证据和运行状态。

| 检查结果 | 含义 | 是否允许写入 |
| --- | --- | --- |
| `supported` | 版本号已知，并且本地结构检查通过 | 可以，仍需退出 Codex、备份和预览复核 |
| `schema-compatible` | 版本号未知或无法读取，但状态 JSON、SQLite 表和项目证据通过结构检查 | 可以，作为结构兼容预览；写入后必须人工核验 |
| `unsupported` | 多个安装版本、状态结构不完整、数据库损坏或必要证据缺失 | 只能扫描和导出诊断 |
| `unknown` | 无法读取版本或结构检查本身失败 | 只能扫描和导出诊断 |

## 结构检查包括什么

- 状态文件顶层是有效对象，账号分区、项目字段、身份映射、项目排序和聊天归属字段类型正确。
- SQLite 数据库可以只读打开并通过 `quick_check`。
- `projects`、`project_roots`、`project_idempotency_keys`、`threads` 表存在，且项目根目录与数据库身份能够互相印证。
- 云端关联、冲突身份、缺失根目录和无法确认的聊天归属继续跳过，不猜测、不解绑、不创建新 ID。
- 写入前再次扫描，确认状态和数据库指纹没有变化；先在 Codex 数据目录外创建备份。

## 平台策略

默认数据目录仍可由 `CODEX_HOME` 指定；未指定时使用各平台的用户 `.codex` 目录。Windows 使用 PowerShell 检测 Codex 进程；macOS/Linux 使用 `pgrep` 检测 `ChatGPT` 或 `codex` 进程。无法可靠检测进程时拒绝写入。

源码流程按平台共享。便携发布包会按 Windows、macOS、Linux 分别构建；不能把某个平台的可执行文件复制到另一个平台运行。平台包缺失时可以使用 Python 3.11+ 和 tkinter 从源码启动。

## 边界

结构兼容不是官方协议，也不是对未来版本的永久承诺。新版本如果改变字段语义而保留旧字段名称，结构检查可能通过；因此写入后仍要求用户检查侧栏、项目目录和旧聊天。任何结构不确定的情况都会退回只读扫描，不通过“强制恢复”绕过保护。

测试使用临时合成项目，覆盖已知版本、未知版本但结构兼容、多安装版本、进程运行、数据库损坏、备份、写入和字段级撤销。测试不替代用户在真实 Codex 中的最终核验。
